# Type bridge: Rust ↔ TypeScript

Rust types and Tauri commands are exposed to the Vue frontend through
[`specta`](https://docs.rs/specta) and
[`tauri-specta`](https://docs.rs/tauri-specta). The generated file is
`src/generated/xap.ts`. The frontend imports types from `@generated/xap`.

This doc covers how the generation works in dev vs release builds, when it's
safe to hand-edit the generated file, and the asset-staging quirk that
catches everyone the first time.

## How a type crosses the boundary

Three pieces have to line up:

### 1. Derives on the Rust type

```rust
use serde::{Deserialize, Serialize};
use specta::Type;

#[derive(Serialize, Deserialize, Type, Clone, Debug)]
pub struct XapDeviceState {
    pub id: Uuid,
    pub secure_status: XapSecureStatus,
    // ...
}
```

- `Serialize` / `Deserialize` — serde, for over-the-wire encoding.
- `Type` — specta, for TS type-definition generation.

Enums use `#[serde(tag = "kind")]` (or `tag = "kind", content = "data"`) so
TypeScript sees a discriminated union. `rename_all` propagates to the TS
output — e.g. `rename_all = "SCREAMING_SNAKE_CASE"` on a Rust enum with
variants `Mo`, `Tg`, … emits `kind: "MO" | "TG" | ...` in TypeScript.

### 2. Tauri command annotation

```rust
#[tauri::command]
#[specta::specta]
pub fn keycode_template_encode(template: KeycodeTemplate) -> Result<u16, Error> {
    template
        .encode()
        .ok_or_else(|| Error("keycode template is incomplete".to_owned()))
}
```

- Function lives in `src-tauri/src/rpc/commands.rs`.
- Both attributes are required: `#[tauri::command]` makes it invokable;
  `#[specta::specta]` makes specta aware of the signature.

### 3. Registration in `main.rs`

```rust
generate_specta_builder!(
    commands: [xap_constants_get, remap_key, keymap_get,
               device_get, devices_get, keycode_template_encode],
    events:   [XapEvent]
)
```

Found in `src-tauri/src/main.rs:109`. If a command isn't in this list,
specta won't emit a wrapper for it.

## When `src/generated/xap.ts` is rewritten

Look at `src-tauri/src/main.rs:113`:

```rust
if cfg!(debug_assertions) {
    specta_builder = specta_builder.path("../src/generated/xap.ts");
}
```

- **Dev mode** (`yarn tauri dev`, `yarn dev`, `cargo run` without `--release`):
  specta writes `src/generated/xap.ts` *on app start*. Each launch overwrites
  the file with the canonical output.
- **Release** (`yarn build`, `cargo build --release`): the path call is
  compiled out. The TS file is whatever was committed.

This means: **the committed `xap.ts` is regenerated every time someone runs
the app in dev**. Treat it as build output: don't expect manual edits to
survive.

## When it's OK to hand-edit `xap.ts`

The file's first line reads:

```ts
// This file was generated by [tauri-specta](https://github.com/oscartbeaumont/tauri-specta). Do not edit this file manually.
```

In practice, there's one legitimate reason to edit it:

**Pre-emptively unblocking `yarn ts-check`.** When you add new Rust types or
commands and want to write Vue code referencing them *before* running `yarn
tauri dev`, you can hand-stub the types so the type-checker passes. The next
`yarn tauri dev` overwrites your stub with the canonical form.

Conventions when doing this:

- Keep the stub structurally identical to what specta will emit (same field
  names, same nullability, same discriminator tags). The diff after the next
  regen should be cosmetic only (doc-comment restoration, ordering).
- Commit the hand-stub if needed to ship a feature branch, then commit the
  regenerated form as a small follow-up labelled "Regenerate xap.ts from
  tauri-specta". See commit `f9cc830f5b16` for an example.
- Don't try to add functionality that isn't backed by Rust. Anything
  hand-added with no Rust counterpart will be silently deleted on the next
  run.

## Generated shape

For each Tauri command, specta emits an `async` wrapper on the exported
`commands` object:

```ts
async remapKey(id: string, arg: RemappingSetKeycodeArg): Promise<Result<null, Error>> {
    try {
        return { status: 'ok', data: await TAURI_INVOKE('remap_key', { id, arg }) }
    } catch (e) {
        if (e instanceof Error) throw e
        else return { status: 'error', error: e as any }
    }
}
```

The `Result<T, E>` shape is `{ status: 'ok'; data: T } | { status: 'error';
error: E }`. Always check `.status` before consuming.

A command that returns `T` (not `Result`) is emitted without the try/catch —
it just awaits the invoke:

```ts
async xapConstantsGet(): Promise<XapConstants> {
    return await TAURI_INVOKE('xap_constants_get')
}
```

Types are exported as plain `export type Foo = ...`. Option / Result map to
`T | null` (specta default — not `undefined`).

## Events

The pattern mirrors commands. `XapEvent` is defined in
`src-tauri/src/rpc/events.rs`:

```rust
#[derive(Clone, Serialize, Type, Event)]
#[serde(tag = "kind", content = "data")]
pub enum XapEvent {
    LogReceived         { id: Uuid, log: String },
    SecureStatusChanged { id: Uuid, secure_status: XapSecureStatus },
    NewDevice           { id: Uuid },
    RemovedDevice       { id: Uuid },
}
```

- Emitted from `src-tauri/src/main.rs:96` via `app.emit("xap", event)`.
- Frontend listens in `src/utils/events.ts:13`:
  ```ts
  tauriEventListener = await listen('xap', async (event: Event<XapEvent>) => {
      eventBus.emit('xap', event.payload)
  })
  ```
- `eventBus` is a local [`mitt`](https://github.com/developit/mitt) instance
  (`src/utils/eventbus.ts`) consumed by `src/App.vue`.

## Asset staging in dev

The bundled-resource case is the second source of confusion.

### Declared in `tauri.conf.json`

```jsonc
"bundle": {
    "resources": [
        "../xap-specs/assets/*"
    ]
}
```

Everything under `xap-specs/assets/` (versioned keycode hjson, the display
config, the lighting JSON files) ships with the Tauri bundle.

### Resolved at runtime

`src-tauri/src/main.rs:127`:

```rust
let xap_specs = app
    .path()
    .resolve("../xap-specs/assets", BaseDirectory::Resource)?;
```

In release builds this points inside the app bundle. In dev builds it points
at the staging directory Tauri keeps under
`src-tauri/target/debug/_up_/xap-specs/assets/`.

### The gotcha

**Tauri only re-stages resources when `tauri.conf.json` itself changes.** If
you edit `keycode_display.hjson` (or any other shipped asset) and restart
`yarn tauri dev`, the running app still reads the stale staged copy.

Workaround — touch the config so Tauri notices something changed:

```sh
touch src-tauri/tauri.conf.json
```

Then restart `yarn tauri dev`. The log line

```
loaded …/keycode_display.hjson (target keycode version: 0.0.8)
```

in the Rust log (and the absence of "keycode display file not found")
confirms the re-stage worked.

Symptoms of a stale stage:

- The "fallback" markers (orange dashed tabs) appear in the picker even
  though `keycode_display.hjson` declares the right `target_keycode_version`.
- Per-key label/description overrides don't take effect.
- The Rust log warns `keycode display file not found at …` on startup.

## Common changes

### Add a new Tauri command

1. Write the function in `src-tauri/src/rpc/commands.rs` with
   `#[tauri::command] #[specta::specta]`.
2. Re-export it in `src-tauri/src/main.rs` (the `use rpc::commands::{...}`
   line) and add it to `generate_specta_builder!(commands: [...])`.
3. Restart `yarn tauri dev`. `xap.ts` gets a new wrapper. `yarn ts-check`
   should pass.

### Add a new Rust type that crosses the boundary

1. Add `#[derive(Serialize, Deserialize, Type, ...)]` to the struct/enum.
   For enums, decide on `#[serde(tag = "kind")]` discriminator format up
   front — changing it later breaks the wire format.
2. Reference the type in a command signature, an event variant, or a field
   of an already-exported type.
3. Restart dev. `xap.ts` picks up the new type definition.

### Add a new `XapEvent` variant

1. Add the variant to `XapEvent` in `src-tauri/src/rpc/events.rs`.
2. Emit it from wherever the event source lives (likely
   `src-tauri/src/xap/client.rs::poll_devices` or similar).
3. Handle it in `src/App.vue`'s `eventBus.on('xap', ...)` switch.
4. Restart dev.

### Edit a shipped asset

```sh
# 1. Edit the file
$EDITOR xap-specs/assets/keycode_display.hjson
# 2. Force re-stage
touch src-tauri/tauri.conf.json
# 3. Restart dev
yarn tauri dev
```

### Commit a regenerated `xap.ts`

If a Rust change produced cosmetic-only diffs in `xap.ts` (doc-comment
restoration, type reordering), commit as a small follow-up:

```
Regenerate xap.ts from tauri-specta

Runtime-regenerated form of the manual type stubs added in <prev-sha>:
<short description of cosmetic diff>. No functional change.
```

Keeps blame readable and confirms the regen matches the hand-stub.

## Verification

- `yarn ts-check` after any Rust change that touches a `Type`-derived
  struct / enum or a `#[specta::specta]` command. If it fails, either your
  hand-stub in `xap.ts` is wrong or you need to restart `yarn tauri dev` to
  regenerate.
- `cargo build -j8 --manifest-path src-tauri/Cargo.toml` confirms the Rust
  side compiles. Specta errors usually surface as missing `Type` derives or
  incompatible `serde` attributes.
- For asset changes: launch `yarn tauri dev` and watch the Rust log for the
  `loaded …/keycode_display.hjson` line.

## Known limits

- **No subagent/release-mode regeneration check.** Nothing prevents committing
  a release build without first running dev to refresh `xap.ts`. A CI hook
  that runs the app once and diffs `src/generated/xap.ts` would catch this;
  not yet present.
- **`yarn tauri dev` is the only canonical regenerator.** There's no
  standalone command like `yarn gen:types`. If you'd rather avoid spinning up
  the full app to regenerate, the codegen path is in
  `src-tauri/src/main.rs:113-115` — wrapping it in a binary target on
  `xap-specs` would be straightforward but isn't done.
